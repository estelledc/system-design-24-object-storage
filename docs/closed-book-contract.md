# Closed-book contract: immutable versions with verified replicas and fenced reclamation

## Reading boundary

This contract was written from the case title alone, before reading the fixed `system-design-notes` chapter. “S3-like Object
Storage” names a problem family, not one API, cloud provider, consistency model, checksum, replication/erasure scheme, storage
medium, region topology, durability figure, or billing contract. Buckets, keys, versions, multipart uploads, metadata, placement,
replicas, repair, listing, lifecycle, deletion, and garbage collection are hypotheses for this lab—not facts about Amazon S3,
Google Cloud Storage, Azure Blob Storage, MinIO, Ceph, HDFS, or any other system. Later research must record confirmations,
conflicts, omissions, and changes instead of silently rewriting this baseline.

## Users and core behavior

### Synthetic object client

1. An authenticated caller creates one lab bucket and writes bounded generated bytes under a stable bucket/key/request identity.
2. A successful write response states the exact object version, content digest, length, metadata commit, and verified replica count.
   It never claims multi-host/region durability, backup, restore, application consumption, or external acceptance.
3. Exact retry returns the original result. Reusing a request or version identity with changed bucket/key/bytes/options conflicts.
4. GET names the key/version read, source replica generation, byte range, digest verification, and repair status. A successful socket
   response without content verification is not an integrity receipt.
5. DELETE creates an explicit tombstone version. It does not silently destroy older addressable versions or prove physical erasure.

### Multipart client

1. A stable upload session binds bucket/key, expected part range/count/total limit, target version policy, and expiry generation.
2. Each part number binds immutable bytes/digest. Exact retry replays; same number with changed bytes conflicts.
3. Completion commits exactly one ordered manifest/result or conflicts. Missing, duplicate, reordered, changed, expired, or unverified
   parts cannot produce a visible object.
4. Aborting/expiring an upload makes it non-completable but does not pretend temporary bytes were already reclaimed.

### Storage worker/operator

1. A placement generation chooses a bounded set of synthetic storage nodes. Each durable replica receipt binds node, content digest,
   byte length, temporary/final path generation, file fsync, parent-directory fsync, and readback digest.
2. Metadata never marks a version visible before the minimum verified-replica threshold is satisfied.
3. A read detects missing/corrupt preferred replicas, falls back to a verified copy, and records repair work without returning
   unverified bytes.
4. Repair, multipart expiry, orphan scan, lifecycle, and GC use worker generations/fences. A stale worker cannot delete or publish
   against a newer manifest/retention view.
5. Ordinary health exposes low-cardinality bytes/object/version/replica/repair/orphan/tombstone/backlog/invariant counts without
   bucket names, keys, version/upload/request IDs, digests, paths, bytes, credentials, principals, or node host data.

### List/metadata consumer

1. One LIST query materializes one prefix/order/version snapshot. Pagination never mixes key mutations from different revisions.
2. Current-key listing, all-version listing, tombstones, not-found, retained-away, and physically reclaimed remain distinct.
3. A metadata row without a verified readable replica is an invariant violation, not a zero-byte object or successful GET.

  acceptance.

## Hypothetical scale envelope

These numbers select failure modes; they are not sourced requirements:

- 100 million objects/day is about 1,157 writes/s average; a 20× burst is about 23,148 writes/s;
- at a hypothetical 1 MiB average, logical ingress is about 100 TB/day before metadata, temporary parts, replicas, checksums, WAL,
  compaction, repair, and versions;
- three full replicas would write about 300 TB/day before protocol and filesystem amplification;
- 99.9% reads from a preferred replica still leaves one in 1,000 reads exercising fallback/repair at large scale;
- 0.01% abandoned or response-lost writes would create 10,000 orphan/reconciliation cases/day;
- one 1 TiB object cannot be retried or buffered like a 1 KiB object, so multipart/streaming/limits are correctness concerns.

The runnable lab will use generated bytes measured in KiB, three directories on one host, and exact receipt counts. It will never
extrapolate same-host directories into independent disk/host/rack/region durability.

## Candidate data and state model

```text
tenant + bucket -> bucket generation + state
bucket + key + version_id -> immutable manifest(content_digest, length, replica_set, created_revision)
bucket + key -> current version pointer (version or tombstone)
content_digest + node_id -> replica generation/state/verified receipt
principal + request_key + operation -> immutable intent digest + original result

upload_id -> bucket/key + state(open|completed|aborted|expired) + expiry/policy generation
upload_id + part_number -> immutable part digest/length + verified temporary replicas
list_query_id -> immutable ordered snapshot + pagination boundary
gc_shard -> worker generation + retention watermark
```

Object keys are opaque bounded identifiers for ordering/lookup; path traversal or filesystem path derivation from a raw key is
forbidden. Content digests name bytes, not authorization or business identity.

## Core invariants

1. **Stable mutation intent.** One request/entity ID binds operation, bucket/key, version precondition, content/part digest, length,
   ordered parts, placement/policy generation, and limits. Exact retry replays; changed intent conflicts.
2. **Object versions are immutable.** A visible version's manifest, bytes, digest, length, metadata, and replica requirement never
   change in place. Overwrite creates another version/current pointer.
3. **Bytes precede visibility.** A version cannot become current/visible until the required replica receipts are durable and verified.
4. **A replica receipt is specific.** Open/write success is not fsync; file fsync is not parent-directory fsync; either is not
   readback digest verification; same-host copies are not independent fault domains.
5. **Temporary-to-final publication is atomic per node.** Write bounded temp, fsync, rename, fsync parent, read back, then report.
   Partial temp/final files remain explainable or reclaimable.
6. **Content address is verified.** File/path/name cannot substitute for byte length and cryptographic content digest at write/read.
7. **Metadata commit is one authority boundary.** Version row, current pointer, verified replica references, and mutation result commit
   together or none are called visible.
8. **Filesystem and metadata cannot be atomically committed.** Replicas written before a rolled-back/failed metadata commit are
   orphans; recovery must adopt exact content or reclaim after a retention/fence, not deny they exist.
9. **Response loss is replayable.** Commit-before-response returns the same version/result; a retry never creates another version.
10. **Placement is versioned.** Node set/required replicas bind the manifest. A stale placement/repair worker cannot publish against
    a newer generation.
11. **Write quorum is not durability math by slogan.** Required verified copies, failure independence, acknowledgement point, repair
    lag, and retention are explicit; v0.1 makes no probability claim.
12. **Reads never return known-corrupt bytes.** Preferred replica length/digest mismatch triggers fallback or typed integrity failure.
13. **Repair is copy-then-verify.** A healthy verified source and current manifest generation are rechecked; repair cannot overwrite
    a newer/different content generation or call an unverified copy healthy.
14. **Missing and corrupt differ.** Missing file, unreadable file, wrong length, wrong digest, absent metadata, tombstone, beyond-
    retention version, and unavailable quorum are distinct outcomes.
15. **Range reads bind full-object integrity evidence.** A returned range names the immutable full digest/version and either verifies
    the full object first or uses an independently authenticated chunk manifest; a byte slice alone cannot prove whole-object state.
16. **Multipart parts are immutable.** One upload/part number maps to one digest/length and receipt. Same part number changed bytes
    conflicts rather than silently replacing the completion input.
17. **Multipart completion is ordered and exactly-once locally.** Exactly the declared part sequence builds one content/manifest and
    durable result. Missing/extra/changed/expired parts fail before visibility.
18. **Abort/expiry are logical before physical.** Closed upload cannot complete; part/object temporary bytes are reclaimable only
    after retention and current-generation checks.
19. **DELETE is a tombstone version.** Current GET becomes not found without rewriting history. Physical deletion is later GC with
    retention/legal-policy boundaries; v0.1 has no legal-erasure claim.
20. **LIST is one snapshot.** Prefix, ordering, inclusion of versions/tombstones, and continuation bind one materialized revision.
    Concurrent PUT/DELETE cannot leak into later pages.
21. **GC is reachability plus retention plus fencing.** Content is deletable only when no committed/current/retained version or open
    upload references it, retention passed, and current GC generation still owns the decision.
22. **Reference count alone is not authority.** Counts can drift after crashes; mark/sweep/reconciliation must derive reachability
    from manifests and preserve ambiguous/recent data.
23. **Retention outlives retries.** Request/version/upload/part receipts and tombstones survive every supported retry/list/version
    horizon. Pruning returns explicit beyond-horizon status.
24. **Backpressure is visible.** Body/part/replica/node/file-descriptor/database/list/repair/GC limits reject/throttle with typed
    receipts; timeout/drop is never called committed.
25. **Keys never become raw paths.** Validation and hashed internal layout prevent traversal, separator ambiguity, case/Unicode
    normalization collisions, reserved names, control characters, or ordinary-log leakage.
26. **Evidence is privacy-bounded.** Ordinary logs/metrics omit bucket/key/version/upload/request IDs, content/part digests, bytes,
    paths, auth values, principals, replica host/device identities, and error payloads.
27. **Self-monitoring is not durability proof.** Metadata health served by the same failed authority cannot prove replica bytes;
    replica count cannot prove backup/restore; no local metric proves client consumption or external acceptance.

## Initial API sketch

Bucket/object routes:

- `POST /v1/buckets` with stable request/bucket identity;
- `PUT /v1/buckets/{bucket}/objects/{key}` with request key, generated bytes, optional current-version precondition;
- `GET /v1/buckets/{bucket}/objects/{key}?version=&range=` returning verified bytes/receipt;
- `DELETE /v1/buckets/{bucket}/objects/{key}` creating a tombstone version;
- `POST /v1/list-queries` and immutable pages bound to one revision;
- `GET /v1/mutation-receipts/{id}` for response-loss recovery.

Multipart/worker routes:

- `POST /v1/multipart-uploads`, `PUT .../parts/{number}`, `POST .../complete`, `POST .../abort`;
- `POST /v1/placements`, `/v1/repairs`, `/v1/orphan-scans`, and `/v1/gc-runs` under expected generations;
- `GET /v1/state` for low-cardinality object/version/replica/upload/repair/orphan/tombstone/invariant signals.

Exact checksum/ETag semantics, key grammar, conditional requests, version IDs, object/part limits, placement/replica threshold,
filesystem publication, read verification, multipart expiry/completion, listing, retention, GC, auth, error vocabulary, and storage
layout remain hypotheses until primary sources are reviewed.

## Failure matrix

| Failure window | Required result |
|---|---|
| caller loses response after metadata version commit | exact key/digest returns original version/result |
| same key/request arrives with changed bytes/options | typed conflict; never another implicit version |
| crash during temporary replica write | no verified receipt; partial temp is retained/reclaimed explicitly |
| crash after one replica fsync/readback | no visible version below threshold; retry adopts exact verified copy or fills missing copies |
| replicas verified then metadata transaction rolls back | files are orphans; no visible object; fenced scan handles later |
| metadata commits then process dies before response | current GET sees exactly one version; retry returns its original result |
| preferred replica missing/corrupt | verified fallback or typed integrity failure; never known-bad bytes |
| repair races overwrite/delete/new placement | expected manifest/placement generation fences stale repair |
| part response lost | exact upload/part/digest replays; changed part conflicts |
| completion races abort/expiry | one locked state wins; no completed object from a closed upload |
| completion crash after version commit | retry returns same version; no duplicate version/content |
| LIST page races PUT/DELETE | every page remains bound to one materialized snapshot |
| DELETE commits | current GET is tombstoned; old retained version stays explicit |
| GC races new reference or stale worker returns | current reachability/retention/generation prevents deletion |
| replica threshold met on one host | receipt says same-host verified copies only; no independent-host durability claim |

1. A clean-room README, source comparison, requirements, architecture, API, operations, threat model, and at least one ADR.
2. Exact bucket/key/version/upload/part/request validation, canonical digests, error vocabulary, path isolation, and privacy tests.

5. True-process crashes covering partial replica write, first verified copy, metadata commit response loss, multipart part/completion,

8. Evidence scans that reject realistic bucket/key/content/credentials/paths and durability/availability/backup/restore/SLA/external
   claims without matching receipts.

## Initial design choices to challenge after source review

- Does the chapter define the exact acknowledgement boundary between storage nodes and metadata visibility?
- What makes a replica durable: write return, fsync, directory fsync, readback digest, or an independent node receipt?
- How are stable retries prevented from creating duplicate object versions or changed multipart parts?
- Does versioning distinguish overwrite, tombstone, old-version access, physical reclamation, and legal deletion?
- Can LIST pagination remain snapshot-stable while keys change?
- What generation fences stale placement, repair, upload expiry, orphan scan, and GC workers?
- Are checksum/ETag, range integrity, corruption, repair, replication, backup, restore, durability, and external acceptance kept as
  separate claims?
