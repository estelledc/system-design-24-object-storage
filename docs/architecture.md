# Architecture and state ownership

## One useful question

The lab asks: after a process dies between local filesystem publication and PostgreSQL visibility, can an operator explain every
file and every logical version without guessing?

```text
synthetic client
      |
      v
JSON HTTP / service validation -- canonical intent + stable identity
      |
      +---- generated bytes ----> node-a/objects/<sha256>.blob
      |                            node-b/objects/<sha256>.blob
      |                            node-c/objects/<sha256>.blob
      |                            temp -> file sync -> rename -> dir sync -> readback
      |
      v
PostgreSQL 17 authority
  buckets / mutation_receipts / expiring write_intents
  object_versions -> object_heads
  replicas / version_replicas
  multipart_uploads / multipart_parts
  list_snapshots
  repair_tasks / maintenance_generations
```

The arrows are deliberately not one distributed transaction. Bytes precede metadata. A crash can create an orphan, but metadata
must never expose an unverified version.

## Write state flow

1. Validate synthetic principal, request key, bucket/key, generated-byte spec, precondition, and size.
2. Canonicalize the immutable intent and calculate the intended content digest and deterministic version identity.
3. Register or renew an expiring, non-visible write intent under the request identity and GC shared fence. A committed result is
   replayed before any filesystem work.
4. For each fixed node, publish or adopt exact content: temp write, file sync, rename, directory sync, reopen, length/SHA-256. An
   adopted file is synced again in this call before its new receipt is issued.
5. If fewer than two receipts verify, return `replica_threshold_not_met`; no version is visible.
6. Begin a short database transaction, take request and bucket/key advisory locks, and look up the mutation receipt.
7. Replay exact committed intent or reject changed intent. Recheck the bucket and optional current-version precondition.
8. Insert immutable version, replica references, current pointer, and original result, then clear the write intent in one
   transaction.
9. Commit. A configured crash hook can terminate here before the response; retry returns the stored result.

Writing replicas outside the transaction prevents filesystem waits from holding database locks. It also means a losing concurrent
precondition or rolled-back transaction can leave content-addressed files. Adoption and fenced GC own that window.

## Read and repair flow

1. Resolve current or explicit immutable version from PostgreSQL. A current tombstone is distinct from a missing key.
2. Visit manifest replicas in deterministic order. Reopen and verify the entire bounded file before using any bytes.
3. Record missing/corrupt replicas as repair work. Serve only a fully verified source, then apply the validated single range.
4. A repair worker takes a task under the current maintenance and placement generation, rechecks the manifest and source, publishes
   the target through the same sync/rename/readback path, and atomically marks the receipt healthy.
5. A stale worker loses at the final generation check even if it already copied bytes. The content-addressed exact file is safe to
   leave for reconciliation; it cannot change logical visibility.

## Multipart flow

```text
open session -> immutable part 1..N receipts -> verify exact ordered manifest
             -> concatenate bounded bytes -> publish final replicas
             -> lock open session -> commit version + completion receipt -> completed

open session -> abort/expire -> closed -> parts remain physically until retention-aware GC
```

Part numbers cannot be overwritten with changed bytes in this lab. That choice makes response-loss replay deterministic and is
explicitly incompatible with Amazon S3's overwrite behavior.

## Listing model

The database is the only current-key authority. Creating a list query runs in a Repeatable Read transaction, selects at most 256
key/current-version records in bytewise key order, and stores the JSON result with the query intent and creation revision. Page
requests address `(snapshot_id, offset, limit)` and never query live heads. The cost is bounded snapshot storage; the benefit is that
later PUT/DELETE cannot alter earlier pages.

## Reachability and GC

A filesystem digest is reachable if referenced by any retained non-tombstone object version, unexpired open multipart part, or
unexpired write intent. The write-intent TTL must outlive the supported bounded write/retry window. An orphan scan records
node/digest/mtime observations but does not delete. GC may remove a file only when:

1. the observation is older than the configured retention cutoff;
2. a fresh database query still finds no reference;
3. the caller owns the current `gc` maintenance generation;
4. the filename is a valid digest inside one configured node directory;
5. deletion is followed by a directory sync and a bounded receipt.

This is lab reclamation, not legal erasure. Snapshots, backups, storage-device remapping, discarded blocks, and external copies are
outside the evidence boundary.

## Authority and concurrency

- PostgreSQL transaction commit: logical visibility and mutation-result authority.
- Local node directory: observed byte-copy state only; a file without a committed reference is not an object.
- Advisory lock by request identity: same request replay/conflict.
- Advisory lock by bucket/key: version/current-pointer/precondition ordering.
- Row lock by upload ID: part/complete/abort/expiry ordering.
- Placement generation: manifest's intended node set and verified threshold.
- Maintenance generation: repair/orphan/GC worker fence.

## Failure-domain statement

`node-a`, `node-b`, and `node-c` are directories under one temporary root. Even if tests use three directory trees and independently
corrupt one file, the copies share process, kernel, filesystem, host, device/controller, power, and CI runner risks. The only valid
claim is “N same-host copies were synchronously published and readback-verified in this fixture.”

## Deferred design work

Independent storage-node processes/RPC, disk/rack/zone placement, quorum/consensus, metadata sharding, authenticated streaming,
chunk manifests, erasure coding, packed files, compaction, lifecycle tiers, encryption/KMS, tenant authorization, quotas, audit,
backup/restore, disaster recovery, multi-region consistency, and S3 compatibility are intentionally absent.
