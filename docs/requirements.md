# Requirements and acceptance boundaries

## v0.1 product slice

One synthetic principal can create bounded lab buckets, write generated bytes as immutable versions, read the current or an explicit
version, create tombstones, materialize list snapshots, perform bounded multipart uploads, repair a replica, scan orphans, and run a
fenced retention-aware GC against three local node directories and one PostgreSQL 17 database.

This is a correctness lab, not a storage product. All data is generated, all object and part bodies are at most 64 KiB, every list
snapshot is bounded, and the HTTP surface is JSON-only with bearer authentication. It is not an Amazon S3 implementation.

## Functional requirements

1. Bucket creation requires a stable request key and returns one durable replayable result.
2. Object PUT accepts only a generated-byte specification, validates bucket/key/limits, and binds request key to canonical intent.
3. PUT writes and verifies replicas before committing an immutable version/current pointer; two verified same-host copies are the
   visibility threshold and normal execution writes all three.
4. Before filesystem publication, an expiring non-visible write intent protects the digest from GC. Its TTL outlives the supported
   bounded write/retry window and it is cleared atomically with a successful version/part commit.
5. Exact retry replays the original result. Reusing an identity with changed intent returns `intent_conflict`.
6. Optional current-version precondition prevents a lost update. A mismatch returns `precondition_failed` without creating a
   version.
7. GET selects current or explicit version, distinguishes tombstone/not-found/integrity failure, verifies full length/SHA-256, and
   may return one validated byte range plus its full-object evidence.
8. Missing or corrupt replicas never serve bytes. A healthy fallback produces a degraded receipt and durable repair work.
9. Repair requires the current placement and worker generation, rechecks a healthy source and manifest, publishes a verified copy,
   and rejects stale work.
10. DELETE creates an immutable tombstone version and replayable result; retained historical data is not silently erased.
11. Multipart initiation binds bucket/key, exact expected part count, total bound, and expiry generation. Parts are immutable and
    independently replicated/verified.
12. Completion requires exactly parts `1..N`, recomputes the ordered final bytes/digest, writes final replicas, and commits one
    visible version/result. Abort/expiry and completion are mutually exclusive under a row lock.
13. LIST materializes one key-ordered current-state snapshot. Pagination reads only that stored array even after later PUT/DELETE.
14. Orphan scan derives live digests from committed non-tombstone versions, unexpired open parts, and unexpired write intents.
    Recent or ambiguous files are never GC candidates.
15. GC requires retention elapsed and the current maintenance generation immediately before deletion. Referenced files are kept.
16. State, logs, and benchmark output expose counts and fixed fixture metadata, not object identities or bytes.

## Limits

| Item | v0.1 limit |
|---|---:|
| bucket name | 3–32 lowercase letters, digits, hyphens |
| object key | 1–96 printable synthetic characters; never a filesystem path |
| generated object/part | 1–65,536 bytes |
| multipart parts | 1–4, exact consecutive sequence |
| completed multipart object | 65,536 bytes |
| list snapshot items | 256 |
| list page | 1–32 items |
| storage nodes | exactly 3 local directories |
| verified replicas required for visibility | 2 |
| request/list/worker identity | bounded ASCII grammar |
| supported range | one inclusive start/exclusive end range |

## Typed outcomes

At minimum: `invalid_input`, `unauthorized`, `not_found`, `current_tombstone`, `intent_conflict`, `precondition_failed`,
`replica_threshold_not_met`, `integrity_failure`, `upload_closed`, `parts_incomplete`, `stale_generation`, `retention_pending`,
`capacity_exceeded`, and `internal_error`. Error responses contain a code and low-cardinality message, never storage paths, SQL,
content, keys, credentials, or digests.

## Evidence ladder

| Receipt | What it proves | What it does not prove |
|---|---|---|
| input accepted | grammar and bounds passed | bytes written or committed |
| replica write returned | runtime call completed | file or directory persistence |
| file sync returned | file data/metadata flush reported | directory entry or hardware independence |
| directory sync returned | parent entry flush reported | another host/region has data |
| readback verified | exact bounded bytes matched length/digest | future readability or backup |
| metadata commit | version/current pointer/result are authoritative locally | caller received response |
| replay receipt | prior committed result recovered | a second external system deduplicated |
| verified GET | selected version bytes matched full digest | file semantics, safety, or client consumption |
| repair receipt | one target copy was republished and verified | independent durability or healed hardware |
| GC receipt | selected unreferenced retained files were removed | legal erasure or every physical copy removed |
| CI green | fixture passed on named runtimes/database/filesystem | production SLA, capacity, backup, or acceptance |

## Completion gates

- documentation, source identities, and evidence boundaries are internally consistent;
- repository policy, syntax, unit, PostgreSQL/filesystem, process-crash, smoke, benchmark, and high-severity dependency audit pass;
- infrastructure tests never skip because PostgreSQL or filesystem behavior is unavailable;
- at least four true-process kills cover pre-metadata replica publication and commit-before-response boundaries;
- public CI passes Node 22, 24, and 26 with pinned actions and PostgreSQL 17.11;
- no test or README claims S3 compatibility, cloud durability, independent replicas, backup/restore, SLA, production readiness,
  client consumption, or external acceptance.
